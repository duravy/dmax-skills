How session capture works in atlas/web

TL;DR — A MutationObserver records DOM changes into a ring buffer, serializes them to a compact delta format, and flushes batches to /ingest every 5 seconds or 64 KB, whichever comes first. Capture is off by default and enabled per route in config/capture.json. Inputs marked data-private are masked before they ever reach the buffer.

The capture path, step by step

Expand each step to see what runs and where it lives. The full path is about 300 lines and costs roughly 1.2 ms per second of active recording on a mid-range laptop.

1 · Observe the document capture/recorder.ts:34

A single MutationObserver is attached to document.documentElement with subtree, attributes and characterData enabled. One observer for the whole page keeps the callback count flat no matter how many components mount.

Masking happens here, not later: any node inside a [data-private] subtree has its text replaced with a run of bullets before the record is created, so unmasked content never enters memory.

2 · Serialize to deltas capture/serialize.ts:12

Each node gets a stable integer id on first sight, held in a WeakMap. Subsequent records reference the id rather than re-describing the node, which is what keeps a long session from growing quadratically.

The output is a flat array of tuples — [op, id, payload] — chosen over JSON trees because it gzips roughly 4× better on repetitive mutation streams.

3 · Batch in a ring buffer capture/queue.ts:20

Records land in a fixed 2 MB ring buffer. When it wraps, the oldest records are dropped rather than the newest — a truncated beginning is more useful than a truncated end when you're investigating something that just happened.

4 · Flush to the collector capture/queue.ts:78

A flush fires on whichever comes first: a 5-second timer, 64 KB of pending records, or visibilitychange going hidden. The last case uses sendBeacon, so a closing tab still delivers its tail.

Failed flushes retry twice with backoff, then drop. Capture is best-effort by design — it must never be the reason a page stalls.

Opting a route in

You don't touch the recorder. Add the route to config/capture.json and mark any sensitive fields in your template. 

// config/capture.json
{
  "defaultEnabled": false,
  "routes": {
    "/checkout": { "sampleRate": 0.25 },
    "/settings/*": { "sampleRate": 1.0 }
  },
  "maskSelectors": ["[data-private]", "input[type=password]"]
}
// app/routes/checkout.tsx
<input
  name="card"
  data-private
  autoComplete="cc-number"
/>

// nothing else to import — the observer is global
POST /ingest
Content-Encoding: gzip

{
  "session": "s_8f21c",
  "seq": 14,
  "records": [
    [2, 118, { "text": "••••••••" }],
    [1, 119, { "tag": "div", "parent": 118 }]
  ]
}
★
Sampling is decided once per session, not per page view. A user sampled into /checkout stays sampled for their whole visit, so you get complete journeys rather than disconnected fragments.

Gotchas worth knowing

  • Masking is by subtree, not by field. Marking a wrapper data-private masks everything inside it, including labels and helper text you probably wanted to keep.
  • Canvas and video are never captured. They serialize to a placeholder rectangle. A replay of a chart-heavy page will look emptier than the real thing.
  • The buffer is per tab. Two tabs on the same route produce two independent sessions, and neither knows about the other.
  • Sample rates multiply. A route at 0.25 inside a project already sampled at 0.5 captures roughly 12.5% of sessions, which surprises people looking for their own replay.

FAQ

How do I capture my own session for debugging?
Set localStorage.atlasCapture = "force" before loading the page. It overrides the sample rate for that tab only and is ignored in production builds.
Where does the data go?
The collector writes to object storage with a 30-day lifecycle rule. Nothing is retained past that window, and deletion requests purge by session id.
Does it work with a strict CSP?
Yes — the recorder ships in the main bundle and opens no workers or blobs. It needs only connect-src for the collector origin.
What's the overhead on a slow device?
Roughly 4 ms per second of recording on a low-end phone. If the main thread is blocked past 50 ms the observer skips a cycle rather than queueing.
