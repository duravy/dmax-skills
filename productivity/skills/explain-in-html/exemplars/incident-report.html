INC-2026-0139

Duplicate webhook deliveries to all subscribers

SEV-2 Resolved Duration 1h 08m Detected Feb 19 · 09:41 Owner A. Osei
TL;DR

A deploy replaced the webhook dispatcher's Redis-backed delivery lock with a per-process in-memory lock. With six dispatcher replicas running, each event was claimed six times, so every subscriber received up to six copies of every webhook for 68 minutes. We mitigated by scaling the dispatcher to a single replica, then rolled back. Roughly 214,000 duplicate deliveries went out; no events were lost.

Timeline

09:32
dispatcher@4.9.0 reaches 100% of the fleet. The release is routine and passes all canary checks — duplicate delivery is not something the canary measures.
09:34
Impact starts. Every dispatcher replica begins claiming the same events. Outbound delivery volume rises roughly 6× while the event rate stays flat.
09:41
First customer report arrives in support: an integration created six identical records. The delivery-volume alert has not fired — its threshold is absolute, and 6× of a quiet Monday morning is still under it.
09:58
On-call correlates the report with the 09:32 deploy. Initial hypothesis is a retry-loop regression, so the retry configuration is inspected first — it is unchanged.
10:21
Reading the diff rather than the config surfaces the lock change. The replica count explains the multiplier exactly: six replicas, six copies.
10:42
Mitigated. Dispatcher scaled to one replica, which makes the in-memory lock correct by accident. Duplicates stop immediately.
11:05
Rollback to 4.8.3 completes and the fleet is scaled back to six. Delivery volume returns to baseline; incident resolved.

Root cause

PR #2247 set out to remove a Redis dependency from the dispatcher's hot path. The delivery lock was rewritten to use a local Set, which is correct for a single process and silently wrong for a fleet. Every replica held its own idea of which events were claimed, so all six claimed all of them.

The test suite did not catch it because the dispatcher's tests run one instance. Nothing in the suite exercises two dispatchers against one event stream, so a class of bug that only appears with concurrency has no test that could fail.

Detection was slow for a separate reason: the delivery-volume alert uses an absolute threshold rather than a ratio against event volume. A 6× multiplier on light traffic stayed below it, so the first signal was a customer rather than a monitor.

dispatcher/src/claim.ts
async function claim(eventId: string) {
- const held = await redis.set(`claim:${eventId}`, id, "NX", "EX", 30);
- return held === "OK";
+ if (claimed.has(eventId)) return false; // local Set
+ claimed.add(eventId);
+ return true;
}
